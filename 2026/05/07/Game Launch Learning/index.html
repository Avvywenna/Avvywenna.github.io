关于Unity项目在编辑器模式下启动时会发生什么

一、域和场景的重载

在按下 Play 按钮之后，Unity 首先会重新加载 AppDomain，这意味着会重置所有脚本的静态变量、事件监听等全局状态。重载的过程是会先销毁当前的 AppDomain，然后创建一个新的。如果希望某些代码在 Unity 进入 PlayMode 的时候自动执行时，可以使用 [RuntimeInitializeonloadMethod] 特性，相当于运行时的Main入口（并不是真的）。

之后，Unity会尝试加载场景，如果在 EditorSceneManager 设置了 playModeStartScene, 那么就会加载被设置的场景，否则，会加载当前 Hierarchy 里的Scene文件。默认情况下，加载的时候会从硬盘里重新实例化场景（而不是直接用 Hierarchy 里面的）

二、资源加载和场景初始化

Unity完成重载之后，下一步是加载场景中的 GameObject 以及其组件，处理模型、纹理、材质等资源的引用。这些 GameObject 会先在内存中实例化，但是此时还没开始运行游戏逻辑，有关这些 Gameobject 的脚本的生命周期还未开始，这些过程会在下一帧完成。

三、脚本生命周期启动

Awake: 在 GameObject 实例化后、在任何 Start 之前被调用，用于初始化脚本引用和初始状态。

OnEnable：紧随 Awake 之后，在对象被启用时调用

Start：在所有的 Awake 和 OnEnable 之后、在第一帧的 Update 之前调用，用于脚本一次性设置，通常游戏自身的业务逻辑会在 Start 开始执行，如热更检查、Lua 加载、场景加载以及系统功能初始化等。在Start之后，Unity 就开始运转完整的引擎主循环：每一帧依次执行输入处理、Update、FixUpdate、动画更新、渲染管线。

渲染管线：每一帧都会进行剔除、排序、绘制等操作，最终将3D场景渲染到 Game 视图中。

基于上述流程的一些游戏启动优化

  • 避免在 Awake 和 OnEnable 执行耗时操作。这些耗时操作会导致主循环的开始时机，优先考虑在 Start 中初始化
  • 大型场景会引起大量资源的加载，应该使用异步加载并设计合适的加载界面
  • 对于大型项目可以考虑使用可配置的进入 PlayMode 功能，提升开发阶段的迭代速度
  • 使用 Profiler，分析定位启动瓶颈，检查域重载、场景加载、脚本初始化的时间消耗

关于Unity应用在非编辑器模式下启动时会发生什么

一、应用入口

我尝试查找过相关资料，但是能找到的信息不是很全面，只能说下我大概的理解，其中有较大程度的推测。

在 Unity 构建对应平台的应用时，会将对应该平台的入口脚本一起构建到包体中。例如在 Android 平台，入口脚本通常是 UnityPlayerActivity 或其自定义的子类，在 UnityPlayerActivity 的 OnCreate 方法中，我们可以执行一些平台相关的逻辑0；在IOS平台，也会有类似的入口脚本以及用于应用预处理的接口

这些入口在其他的 App 都会存在，例如 Android 系统的应用，都会有一个用于启动的 Activity；IOS 也类似

二、Unity 调起

对于 Unity 应用来说，在系统拉起应用后，Unity 自身的 C/C++ 核心开始运作

通过性能分析器可以捕获到两个关键方法的运行记录

  • UnityInitApplicationGraphics：完成对图形设备、大量内部系统（如资源系统）的初始化，后者会为后续加载资源做准备。此阶段的耗时与项目 Resources 文件夹中的文件数量正相关
  • UnityLoadApplication：加载并初始化项目的第一个场景，涵盖反序列化所有场景数据、编译着色器、构建寻路网格等一系列繁重工作

三、项目初始化

从这里开始项目的启动流程就跟在编辑器模式下启动时一样了，接下来是 “资源加载和场景初始化” 和 “脚本生命周期启动”

项目初始化过程中发生了什么

在对Unity项目从启动到进入到第一个游戏场景的过程有了一个大概的了解之后，我们可以确定的一件事是我们需要将游戏初始化的工作放在第一个场景中，而第一个场景是Unity启动之后自动实例化的

对于大多数游戏，在游戏启动的首个场景中，会进行版本检查、资源热更以及登录流程等，对于一些更复杂的游戏在首个场景中会做的事情就会更多

通常我们会在场景中挂一个物体，然后在物体身上挂一个Monobehaiver脚本，然后在Start生命周期方法中开始以上的这些初始化流程

上述初始化流程是我们在游玩时直观看到的，同时也会有一些看不见的初始化工作如Lua环境初始化

市面上常见的Unity开发模式是Unity + Lua进行开发，Lua是用于实现业务的脚本，由于它易于热更的特点成为游戏开发的热门脚本。除了Lua，项目的一些底层业务通常是用C#编写，如网络模块、资源管理模块等，这类代码在项目研发期间编写，并且在项目上线后基本不会修改，一旦修改由于不方便热更所以只会重新出包

在使用Lua编写游戏业务时，往往需要访问Unity侧的API，例如修改文本显示、修改对象位置等。但是Lua不能直接跟C#相互通信，但是好在Lua底层向外提供了访问虚拟机的一些C++接口，而C#也可以通过dll访问第三方的C++接口，所以这种情况下只需要引入第三方工具，来处理Lua跟C#在底层的交互就可以了

这样的工具有很多，例如sLua、toLua、XLua、NLua等，这些工具的特点都是负责对Lua运行环境的初始化、内存管理、交互实现，在本篇中，我们将讨论使用XLua来实现Lua跟C#交互的情况。

另外在Unity运行时，它本身是不会自动运行Lua脚本的，所以你编写的Lua脚本它是如何被加载以及在内存中运行起来的呢，答案是在游戏初始化时会去启动Lua虚拟机，并且会初始化项目自身的Lua运行环境，这样你的Lua脚本才得以运行，不过这里只是一个比较笼统的说法，只是想简单介绍会有这样的一个环节，具体的初始化逻辑会在将来更详细的介绍

接下来将详细介绍一下我所了解的游戏启动初始化流程

  • 资源更新检查
  • Lua业务启动
  • 其他模块启动

我们在场景中添加一个挂有初始化脚本组件的物体，这样在场景实例化之后，Unity会在其生命周期中调用 Start 方法，我们的项目初始化流程从这个 Start 开始。

资源更新

一、什么时候需要资源更新

资源更新发生在游戏内容发生迭代的时候，这里的资源指游戏脚本和资产。资源更新的方式有两种，一种是应用版本发生变化，需要下载最新版本的安装包覆盖安装，这里的应用版本指的是Unity 项目设置里的版本；另一种是资源版本发生变化，发生在游戏的bug修复、系统迭代等，这种情况下游戏会在启动的时候从服务器拉取最新的资源版本进行下载更新。

还有第三种资源更新方式，前两种在某种程度上都要重启游戏，第三种是可以在游戏在线的时候实现。具体来说是通过服务端推送lua脚本字符串，通过lua dostring的方式执行，可以实现运行时替换函数执行逻辑、或者调用Unity侧代码进行其他行为，然而实际上并没有改变应用本地的资源，当游戏重启之后，内存会丢失，原本有问题的代码依旧存在，所以一般这种方式用于对大规模线上问题的紧急修复，同时会推送一个热更版本，这样应用重启之后才会更新到最新的修复。

这里我主要介绍资源版本更新的情况

二、全量更新和增量更新

资源更新手段有全量更新和增量更新

全量更新是指通过从服务器下载完整的文件进行更新，这种方式所产生的流量较多，通常用于应用新增系统、或某些资源版本差异较大的情况，好处是实现简单

增量更新是指通过从服务器下载的资源补丁文件，将补丁文件通过某种算法应用到对应的旧版本资源文件上，最终得到新版本的资源文件，通过这种方式来更新所产生的流量更小，通常用于小版本优化，bug修复等，缺点是依赖本地文件完整性，实现复杂，每个补丁文件通过某种二进制差分生成，如 bsdiff 或 hdiff

这两者不是冲突的关系，在某一次更新中对于新增的资源通过全量下载，对于已有的文件则通过Patch方式进行修补（差异小的话），这是一种两者结合的更新策略

对于客户端来说，需要同时实现对两种更新方式，对于服务器来说则需要根据客户端版本来选择返回有哪些资源以及怎么更新等等，这部分内容将来会继续讨论（让我先学）

三、热更流程

  • 全量更新

    • 加载本地资源清单

      在资源打包的时候，通常伴随输出一份资源清单文件，这个清单记录了本次打包的资源版本以及所有打包出来的资源的路径、分包类型、md5、大小等信息，并且不同的build版本对应的资源清单之间都存在一些差异，这些差异的文件在游戏应用内按照不同的版本号存储

      当用户首次安装应用时，应用自带一份包体版本的资源以及资源清单，例如我安装的应用版本是v1.0.0，那么在包体里就会有一个../1.0.0/路径，下面存放它的清单文件和对应的资源

      假如在运行应用时进行了一次热更，此时热更版本是当前包体的最新资源版本，热更完成后在应用内就会多一个新的版本目录如../1.0.2/，内部同样会管理一份自身版本的清单文件

      在加载本地资源清单的时候需要加载最新资源版本下的清单文件，为了知道本地当前最新的资源版本是哪个，我们可以在一个文本中记录下当前的最新资源版本，在每次完成热更之后将其内容修改为最新的版本号

    • 请求服务器资源清单

      在资源服务器上会存储各个版本的资源清单以及对应的资源，跟客户端本地类似，通过指定的版本号可以请求对应的清单数据，在此之前我们需要先知道当前包体的热更版本是多少

      热更版本通过向版本管理后台请求得到，在客户端里通常存储着版本管理后台的地址，客户端启动时，首先会从版本管理后台请求当前包体的服务器环境配置数据，后台会返回这个包体版本对应的热更版本、资源服务器地址等等信息，其中热更版本用于给客户端请求对应资源清单，资源服务器地址用于请求下载清单中的资源，还有其他的数据用作其他用途，具体实现根据项目情况实现

    • 资源处理

      我们的目的是替换或者新增资源，为此有多种情况需要处理

      • 需要换新包

        从后台请求得到的热更版本号，如果跟当前应用版本的Major或Minor不匹配，意味着包体的架构发生了较大的变化，是必须强制换新包才能游玩，这部分具体业务逻辑具体跟各自项目有关

        当然了，就算是重新安装新包，在运行的时候也还是会进行一次这里的流程

      • 基础包外资源

        在请求服务器环境配置时，返回的数据可能会指向不需要资源更新的情况，这通常是游戏刚刚开服，只发布了第一个版本的包体，没有发布其他的修复版本。但是通常这不意味着我们就可以直接进入游玩，之前提到厂家会为了减少首包体积，只会在安装包里放入基础可供运行的资源，然后将其他的资源如开幕剧情、基础语音等资源放在包外，并且这些资源会被标记为基础的包外资源，我们在打开应用时，这部分的资源是必须要下载的（如果没有这些资源就会阻碍游戏进行）

        在需要资源更新的情况下，除了热更版本新增资源外，如果检测到基础包外资源为空，也是需要下载的

      • 在本地已存在的资源

        对于本地已存在的资源需要区分两种情况，第一种是这个资源存在于最新版本目录下的，当用户下载中途重启了应用，此时本地已经下载了一部分的新资源，因此这里需要检查是否有这样的资源；第二种是这个资源存在于旧版本（或者叫本地版本）的目录中，由于我们在进行全量下载，会有旧版本的资源跟新版本的资源冲突，我们需要将它们找到

        对于第一种情况的资源，我们需要确保它们是否下载完整，一种常见的方法是比较MD5，如果MD5不一致，那么这个文件就要重新下载

        对于第二种情况的资源，我们同样需要通过MD5对比来验证文件一致性，如果不一致，就放入待下载列表，同时旧资源需要删除，否则这个资源不需要重新下载，但是需要将它从旧版本的目录移动到新版本目录中

      • 在本地不存在的资源

        下载到热更版本的目录下

  • 增量更新

    • 请求补丁版本列表

      后台会管理不同热更版本下，修补到最新版本所需要的补丁文件，例如当前最新版本是v1.0.5，从版本v1.0.1修补到最新版本的补丁资源，跟从版本v1.0.3修补到最新版本的补丁资源是不一样的

      同时对于有些资源版本则不会提供补丁资源（例如当版本差异过大时），因此在后台首先会管理一个版本列表，列表中记录针对最新版本生成了补丁文件的资源版本，我们需要请求这个列表以确认自己的资源版本是否需要进行补丁更新

      至于服务器是如何管理这个列表以及补丁是如何生成的目前并没有深入了解过，后面有计划会整理一下相关资料

    • 请求补丁资源列表

      如果后台有当前资源版本的补丁文件，就需要下载这些补丁列表，然后对本地资源进行修补

  • Task / Parallel

    上述处理资源的流程中，将旧版本资源移动到新目录，以及对已下载资源进行MD5校验等，都需要通过并行Task的方式来高效处理多个文件的读写操作

    Task详解

  • 文件完整性检查

    除了对比MD5，还有以下几种常见且可靠的方法，适用场景略有不同

    1. 其他哈希算法

      • SHA-1 / SHA-256：更安全，碰撞概率极低。SHA-256 常用于软件签名和区块链
      • CRC32 / CRC64：主要用于检验传输错误，速度极快，但安全性远低于MD5
      • BLAKE3 / xxHash：速度极快的非加密哈希，适合超大文件（如十几GB的虚拟机镜像）的快速对比

    2. 按字节逐位对比，不依赖任何算法，大力出奇迹

      • 优点：绝对准确，不会出现哈希碰撞
      • 缺点：需要访问源文件，且耗时较长

    3. 分块哈希与滚动校验

      • 将文件切成固定大小块，分别计算每块的哈希，用于快速定位哪一段数据不一致
      • 使用滚动校验和，高效找出两个文件之间的差异部分，常用于增量同步

  • 文件下载框架

    下载框架支持多任务并行下载，每次创建多个下载任务，任务启动前会处理断点续传问题，然后再调用给下载终端，这里的下载终端是UnityWebRequest，UnityWebRequest支持从指定位置开始传输文件

    并行下载伪代码

    在下载过程中，通过在Monobehavier的Update方法中监听正在进行的job的进度用于给监听器同步（实际上是监听UnityWebRequest任务的状态）

Lua业务启动

一、Lua加载器

lua loader 根据指定路径（如A.B.C）加载lua文件返回字节数据，lua代码会被以某种数据格式打包为bundle，在加载时需要将bundle文件读取为二进制流来进行解析成原来的文件

加载器接收的参数是 require(“这里面的字符串”)，并且返回UTF8编码的byte[]

二、XLua luaEnv初始化

创建lua状态机Lua_State，在内存分配空间

注册xlua库、lua库、CS表等

注册lua loader

三、lua业务启动

完成了Lua_State的启动以及XLua的初始化后，通过luaEnv.DoString(…) 来加载并运行lua业务入口

lua业务入口通常需要：

  1. 初始化系统模块、公共表、配置表、网络模块

  2. 绑定Unity生命周期函数如Update、fixUpdate、OnApplicationQuit等

  3. 进入登录页面（此时算正在进入了游戏，后续走正常的lua业务，业务中需要跟C#交互时由XLua的各个组件做转发调用）
