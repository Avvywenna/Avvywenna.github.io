一、Image 的继承体系与接口

Image 首先是一个 Graphic，因此它会参与到 UGUI 的统一重建流程（CanvasUpdateRegistry → PerformUpdate → OnPopulateMesh）。除此之外，它还通过继承和实现多个接口获得了额外的能力：

基类 / 接口 作用
MaskableGraphic 支持 RectMask2D 和 Mask 的裁剪效果
ILayoutElement 参与布局系统的自动尺寸计算（CalculateLayoutInput、minWidth/preferredWidth 等）
ICanvasRaycastFilter 支持基于像素透明度的精确点击过滤
ISerializationCallbackReceiver 处理序列化回调（如 Sprite 修改后的脏标记触发）

二、核心成员解析

1. sprite、overrideSprite 与 activeSprite

这三个字段是 Image 中与 Sprite 引用相关的核心成员，它们之间的关系如下：

字段 说明
sprite Inspector 中显示的 Source Image，是 Sprite 的永久引用
overrideSprite 脚本内成员，不在 Inspector 中显示。用于临时覆盖当前显示的 Sprite
activeSprite 只读属性，优先返回 overrideSprite，若为 null 则返回 sprite

activeSprite 的实现逻辑：

返回 overrideSprite ?? sprite

这意味着：

  • 当 overrideSprite != null 时，Image 显示的是 overrideSprite，而非 sprite
  • 将 overrideSprite 设为 null 后，Image 立即恢复显示 sprite
  • Image 中所有涉及 Sprite 的计算（网格生成、尺寸计算、射线检测等）都通过 activeSprite 进行

典型使用场景：按钮的悬停/按下状态切换。通过修改 overrideSprite 实现临时图片替换，无需手动保存和恢复 sprite 的原始值。

2. m_AlphaHitTestMinimumThreshold

这个字段用于实现基于像素透明度的精确点击过滤。当启用时，只有点击位置所在像素的 Alpha 值大于等于该阈值时，才会响应点击事件。

启用条件（缺一不可）：

  1. activeSprite != null 且 activeSprite.texture != null
  2. Sprite 纹理未使用 Crunch 压缩（sprite.texture.isCrunched == false）
  3. Sprite 纹理开启了可读写模式（sprite.texture.isReadable == true）

为什么需要可读写模式？因为 IsRaycastLocationValid 需要调用 texture.GetPixelBilinear 采样像素 Alpha 值，而该 API 要求纹理可读。

性能注意事项：GetPixelBilinear 是 CPU 端的纹理采样操作，在每帧射线检测时都会被调用。如果场景中有大量启用了透明度过滤的 Image，可能会产生可观的 CPU 开销。

3. DisableSpriteOptimizations

这个方法的字面意思是禁用对 Sprite 的优化。内部是将两个跳过相关的变量设置为 null。

在默认情况下，当修改 sprite 的值时，Image 会检测新旧两个值是否一致。如果一致，那么 Image 就不会参与到 UGUI 的重绘流程，从而可以节省一些性能。

通过调用这个方法，则可以强制让 Image 参与重绘流程。通过引用查找会发现唯一调用的地方是在 ImageEditor，即我们在 Inspector 上修改 sprite 时，会强制刷新。

4. pixelsPerUnit 系列字段

字段 来源 作用
spritePixelsPerUnit activeSprite.pixelsPerUnit Sprite 自身设置的 PPU 值
m_CachedReferencePixelsPerUnit canvas.referencePixelsPerUnit Canvas Scaler 上的 Reference PPU
pixelsPerUnit spritePixelsPerUnit / m_CachedReferencePixelsPerUnit 实际用于尺寸转换的系数
multipliedPixelsPerUnit pixelsPerUnit * (m_TextureScale 或 1) 用于九宫格/平铺等模式的额外缩放系数

这些字段共同负责 Sprite 像素尺寸 → Unity 单位 → UI 像素尺寸 的转换：

关于Sprite的尺寸转换

当一个 Sprite 被渲染到屏幕上时，通常不会直接按原始像素大小渲染。由于设备分辨率不同，同一个 Sprite 如果要在不同的设备上做到相同的效果（如相对位置、相对大小）一致，那么就需要通过某些中间值进行转换适配，这个中间值就是 Unity 的单位。

在 Sprite 的 Inspector 上提供了一个参数，名叫 Pixels Per Unit，直译为“像素每单位”。该值默认为 100，意味着假如 Sprite 的像素大小是 100x100，那么转换为 Unity 单位就是 1x1。

然而这个 Unity 单位并不是最终渲染的尺寸，我们还需要通过 Canvas Scaler 上的 Reference Pixels Per Unit 来转换为 Transform 的尺寸。这个值默认也是 100。根据上述结果，如果再结合这个值进行转换，会发现 Image 如果使用了这个 Sprite，那么它的原始大小就是 Sprite 的原始像素大小。

这里说的“原始大小”是指调用 SetNativeSize 时设置的大小。

在 SetNativeSize 方法中，我们可以看到 Sprite 的像素尺寸是如何转换到 RectTransform 的尺寸的。以宽度举例，简单来说就是：

w = activeSprite.rect.width / (spritePixelsPerUnit / m_CachedReferencePixelsPerUnit)

其中 activeSprite.rect.width 是 Sprite 原始像素宽度，spritePixelsPerUnit 是在 Sprite 的 Inspector 上设置的参数，m_CachedReferencePixelsPerUnit 是从 Canvas Scaler 上设置的参数。

关于 pixelsPerUnit：

它的计算公式是：pixelsPerUnit = spritePixelsPerUnit / m_CachedReferencePixelsPerUnit

通过访问 pixelsPerUnit 可以方便地在任何地方将 Sprite 的尺寸转换到 RectTransform 的尺寸。

关于 spritePixelsPerUnit 和 m_CachedReferencePixelsPerUnit：

虽然这两个参数都可以影响 Sprite 的渲染尺寸，但是作用的范围并不一样。前者可以单独对一张 Sprite 进行调整，而后者是关系到整个 Canvas 内部所有 Image 的尺寸。

关于 multipliedPixelsPerUnit：

从字面意思可以看出是在上面的 pixelsPerUnit 上多了一个倍数，而这个倍数默认值是 1。这个成员通常作用于 Sprite 九宫格、拉伸、平铺等场景，会影响这些渲染方式的效果。

5. PreserveSpriteAspectRatio

这个方法用于将 RectTransform 的宽高比调整到跟 Sprite 尺寸的宽高比一致，目的是让 Sprite 可以完整地在 Rect 内展示且不会被拉伸。入口受 m_PreserveAspect 的控制，该值默认为 false，即默认情况下不会自行调整 RectTransform 的尺寸。

6. GetDrawingDimensions

这个方法用于获取在剔除了 Sprite 四周留空区域（padding）之后的有效绘制区域。这个区域通过四条边在坐标系中的位置来表示，分别为（左边界、上边界、右边界、下边界）。

利用这种表示方式，通过两两相交即可得到这个区域的四个顶点。这个设计在网格填充的一些计算中起到比较重要的作用，特别是在 Simple 和 Sliced 模式中。

三、OnPopulateMesh —— 核心网格填充逻辑

不只是 Image，在自己实现 OnPopulateMesh 时，需要给 VertexHelper 填充顶点数据。顶点数据包括顶点坐标、顶点颜色、UV 纹理坐标以及三角形数据。如果直接将 VertexHelper 清空掉然后什么都不做，就不会渲染任何东西（但是不会影响射线检测和事件接收）。

对于 Image 来说，它在 OnPopulateMesh 中主要根据 Image.type 调用多个不同的网格填充方式来完成顶点数据处理。下面逐一介绍。

1.Simple（默认）

这是默认的显示方式，Sprite 会以原始效果渲染，但是会被拉伸或挤压。

根据 useSpriteMesh 变量的值，再选择不同的 API 路径。

路径一：useSpriteMesh == false（默认）

调用 GenerateSimpleSprite 进行顶点填充。这个方法的逻辑比较简单：

  • 根据 GetDrawingDimensions 的结果生成四个顶点
  • 通过 sprite.GetOuterUVs() 获得 Sprite 的纹理空间坐标，同步设置给顶点数据
  • 用这四个顶点的索引绑定两个三角形，完成最简单的顶点填充处理

路径二：useSpriteMesh == true

调用 GenerateSprite 来填充顶点。此时填充的顶点坐标跟纹理坐标不再直接使用 RectTransform 的绘制区域，而是使用 Sprite 的 Mesh 提供的 vertices 和 uv。

不过 Mesh 的顶点坐标不能直接当作 Image 坐标系下的坐标，需要经过一些转换：

对于顶点 vertices[i]，它的坐标 (x, y) 是相对于 spriteBounds（即 activeSprite.bounds.size）存在的。而通过 GetPixelAdjustedRect() 可以得到表示 Image 的绘制区域的 Rect。因此可以得出：

vertices[i] 对应的顶点坐标的 x 分量 = (vertices[i].x / spriteBounds.x) * rect.width

y 分量同理。

另外，由于还需要将 Sprite 的 pivot 与 RectTransform 的 pivot 对齐，代码中会根据这两个轴心的差异计算出一个 Offset，这个 Offset 会被应用在上面计算得到的坐标分量上。

对于纹理坐标，直接应用 Mesh 提供的数据即可。

关于 Rect：Rect 是通过原点位置 (x, y) 和 width、height 来在坐标系中确定一个矩形区域的表达方式。其中原点是 Rect 的左下角，先确定原点，然后再按 width 和 height 进行延展就能确定一个矩形。

关于 useSpriteMesh 在实际项目中几乎不被使用，因为其顶点数量可能远多于 4 个，会破坏合批效率。Unity 保留此选项主要是为了兼容旧版本 Sprite 的导入方式。

2.Sliced（九宫格）

此模式通过 GenerateSlicedSprite 生成网格，适用于边框不变形、中心区域拉伸的 UI 元素（如按钮背景、对话框）。

核心流程：

  1. 获取 Sprite 的 border（左、上、右、下四条边的位置）
  2. 根据 border 和 Image 的绘制区域，计算出 9 个格子的边界坐标
  3. 计算每个格子对应的 UV 坐标（由 OuterUVs和 InnerUVs 组合而成）
  4. 对 9 个格子分别调用 AddQuad，每个格子生成 4 个顶点和 2 个三角形

九宫格的 9 个格子中，四个角保持原始尺寸不变，四条边在对应方向上拉伸，中心区域在两个方向上拉伸。

3.Tiled（平铺）

这种模式下，通过 GenerateTiledSprite 来为平铺模式的 Sprite 生成顶点数据。

在使用这个模式时，Sprite 通过自我重复的方式来填充 Image 的区域。对于有没有 border 的情况，处理方式会不一样（即是否切了九宫格）：

  • 如果切了九宫格，重复的部分就是九宫格的内部区域
  • 如果没有切，就是对完整的 Sprite 进行重复

这里的“重复”具体是什么意思呢？其实就是用 Image 的尺寸除以重复部分的尺寸，得到应该重复的个数。例如 Image 宽 1000，而重复区域的宽是 100，那么在横坐标方向上就会重复 10 次，纵坐标方向同理。

每重复一次，就是相当于在 VertexHelper 中填充 4 个顶点（两个三角形），这 4 个顶点形成的区域就会将重复区域绘制出来。可以发现，重复次数越多，VertexHelper 中新增的顶点数量也会越多。

顶点数量限制：

为了防止顶点数过多导致性能问题，Unity 在生成 Tiled 网格时会检查总顶点数。如果超过 65000（USHORT_MAX），会强制调整 Tile 尺寸使顶点数在限制范围内。

在移动端项目中，Tiled 模式应谨慎使用，因为大量顶点会显著增加 CPU 和 GPU 开销。如需大面积重复背景，建议改用 Shader 方式实现。

4.Filled（填充）

这种模式下，又细分为了 Horizontal、Vertical、Radial90、Radial180、Radial360 这五种填充类型。虽然可选项有五种，但是归根结底可以分为两类。

线性填充（Horizontal / Vertical）

FillMethod.Horizontal 和 FillMethod.Vertical 是最简单的填充方式：

  • 根据 FillAmount 在横向或纵向上插值顶点的 位置 和 UV
  • 支持 FillOrigin（从哪一侧开始填充）和 FillClockwise（是否翻转）

扇形填充（Radial 90 / 180 / 360）

这是 Image 中最复杂的网格生成逻辑，表面上是围绕不同的原点进行扇形切割，其核心思想是 “将扇形拆分为多个 90° 的单元”：

类型 组成 说明
Radial90 1 个 90° 单元 基础单元
Radial180 2 个 90° 单元拼接 水平或垂直镜像
Radial360 4 个 90° 单元拼接 完整圆环

这种叠加方式有效的前提是对 Radial90 本身的扇形切割处理简单有效，在此之上的叠加只需要根据顺序给定不同的坐标范围就可以了

RadialCut 方法解析：

RadialCut 是扇形填充的核心算法，接受以下参数：

参数 说明
xy 四个顶点的坐标数组（顺序：左下、左上、右上、右下）
cos Mathf.Cos(fillAmount * 90°)
sin Mathf.Sin(fillAmount * 90°)
invert 是否翻转旋转方向
corner 轴心点的索引（0=左下，1=左上，2=右上，3=右下）

顶点演化过程（假设给定的区域是正方形，以左下角为轴心，顺时针旋转为例）：

  1. 当旋转轴从零开始旋转时，轴会先跟上边界相交，并且随着交点右移，被绘制的图形会慢慢变多，直到交点到达对角顶点。在这个过程中，被绘制区域一共由四个顶点组成，按逆时针方向数分别为三角形：原点 → 左上顶点 → 上边界交点 → 上边界交点（两个交点退化为同一个）。

    这里旋转轴跟上边界的交点虽然只有一个，但是实际上是原始矩形的右上角和右下角由于旋转轴跟边界相交退化而来的，这两个顶点退化为同一个交点。

    该交点的横坐标通过某种方式从左边界和右边界横坐标中进行插值得到，而纵坐标则固定为上边界的位置。

  2. 随着 fillAmount 继续增加，旋转轴会来到跟右边界相交，此时图形已经绘制了超过一半的区域。此时绘制图形顶点变为四边形：原点 → 左上顶点 → 右上顶点 → 右边界交点。

    此时只有原来的右下顶点退化成了交点。交点的横坐标固定为右边界位置，纵坐标则是上边界跟下边界进行插值。

  3. 最后当 fillAmount = 1 时，图形的四个顶点则完全是原矩形的顶点，此时图形完全被绘制出来。

插值的计算方式：

还记得方法参数中给了 cos 和 sin 吗？代码中正是通过这两个值来进行插值计算。

  • 当 sin > cos 时，这意味着在正方形区域中旋转轴划过的角度大于 45°，此时旋转轴跟右边界相交。交点的纵坐标 y = Mathf.Lerp(y0, y2, cos / sin)

    其中 y0 表示下边界，y2 上边界。过渡值 r = cos / sin。随着角度继续增大，cos 跟 sin 的比值越来越小，y 会逐渐从上边界靠近下边界，反映到交点上就是从对角顶点逐渐移动到它的下一个顶点。

  • 当 cos > sin 时，交点的计算方式同理（与上边界相交，横坐标插值）。

注意：上述推导基于正方形假设。在非正方形矩形中，旋转轴扫过的角度与 FillAmount 不是线性关系，但由于代码中的插值计算是在正方形假设下进行的，因此实际效果会略有偏差。这是 UGUI 的一个已知设计取舍。

注意到，随着 fillAmount 匀速变化，旋转轴转过的角度在正方形内是匀速的。例如当 fillAmount = 0.5 时，扫过的角度是 45°。然而在非正方形中，实际扫过的角度却不是 45°。

代码的这个做法可以想象为：程序先基于正方形确定交点位置，然后将正方形拉伸到原来的形状—— 当然实际上代码并没有进行这样的操作，只不过这种理解方式可以帮助解释最终效果上的一些偏差。

如为什么fillAmount=0.5时，图形不是正好切开一半等等

关于轴心点的通用化：上面将原点假设为矩形左下角。但是单论 Radial90 本身就有 4 个不同方向的顶点。回顾上面四个顶点的假设，其实完全可以换一种表述：

  • 原点：给定轴心点，在上面假设为左下角，记为 i0
  • 左上顶点：表述为原点的下一个顶点，记为 (i0 + 1) % 4
  • 右上顶点：表述为原点的对角顶点，记为 (i0 + 2) % 4
  • 右下顶点：表述为原点的上一个顶点，记为 (i0 + 3) % 4

通过这种表述转换，以及简单的索引计算，就可以将上述的流程通用到所有情况的顶点。

最终，不管是 Radial90、Radial180 还是 Radial360，本质上都是划分为多个矩形的 90° 扇形切割，然后根据划分情况给定不同的顶点坐标、原点等，从而实现完整的扇形切割效果。

四、总结

本文对 Image 中的重要成员进行了介绍，并且了解了 Image 是如何进行网格填充的，对后续自定义 Graphic 的绘制方式提供了参考。

核心概念 关键点
Sprite 引用 activeSprite 优先返回 overrideSprite，其次返回 sprite
透明点击过滤 通过 m_AlphaHitTestMinimumThreshold 实现，需纹理可读且未使用 Crunch 压缩
尺寸转换 SetNativeSize() 计算公式涉及 spritePixelsPerUnit 和 canvas.referencePixelsPerUnit
Simple 模式 默认生成 4 个顶点；useSpriteMesh = true 时使用 Sprite 自带网格
Sliced 模式 九宫格生成 9 个格子，边框不变形
Tiled 模式 平铺生成大量顶点，受 65000 顶点限制
Filled 模式 线性填充和扇形填充（Radial 90/180/360），核心算法为 RadialCut

理解 Image 的网格生成逻辑，不仅能在实际项目中根据需要选择合适的渲染模式，也为自定义 Graphic 组件提供了参考。特别是扇形填充的切割算法，展示了对顶点数据进行动态控制的思路，在制作技能冷却、进度条等 UI 元素时非常有用。
