GitHub图床搭建

Created2026-07-17|Updated2026-04-27|伊地知虹夏的备忘录
|Post Views:

GitHub

  1. 注册并登录
  2. 新建一个仓库(Repository), 该仓库将会用于存储你上传的图片资源，注意仓库要保持Public的可访问性（默认就是）
  3. 点击右上角头像，在弹出的选项中找点Setting，点击会打开你的Profile设置页面，在左侧列表最下方找到Developer Settings选项，点击会打开DevelperSetting
  4. 在页面的左侧选项中找到Personal access tokens, 选择其中的”Tokens(classic)”选项，在右侧会看到你的开发者Token列表
  5. 在页面右上方，找到”Generate new token”, 点击之，遂选择”Generate new token(classic)”, 会进入到创建新token的页面
  6. 在页面，最上方Note中填写你的Token的名称，如”Token-Photo”, 接着在Expiration下选择这个Token的有效期，支持指定固定的过期时间或者无限期，当Token失效之后，需要来到这里对需要的token重新设置过期时间，在Expiration之后是”Select scopes”, 作为图床只需要勾选第一个选项”repo”即可, 最后点击最下方的”Generate token”完成创建.
  7. 在页面的引导下，它会提醒你及时保存token，不管如何，我们最好在创建完token之后保存下来以防不备之需，另外在后面的PicGo设置中，我们也确实需要这个token，所以在这里点击复制把token保存在你还会找到的地方

题外话

我曾考虑过图床仓库的可访问性是Public的话，会很不安全吧，于是将仓库可访问性改为私有，结果是jsdelivr无法访问（会提示Failed to fetch version info for xxxx）。

我说那好吧，如果是其他的图床方案的话应该就不会有这种问题了，不过现在没时间更换其他方案，那只能先把仓库改回来Public。结果改回来之后，jsdelivr的访问依然是失败。查了一些相关资料，大致是说跟cdn缓存相关，就算我用了jsdelivr的Purge CDN cache也没有明显效果（至少没有立刻生效）。

目前看下来的其中一种解决办法是在原来的jsdelivr链接上仓库名后面加上@main或者@master，这样可以正常访问（前提是仓库保持Public）。

在通过https://cdn.jsdelivr.net/gh/Avvywenna/Photo/直接访问的时候，会看到jsdelivr实际上访问的是master的分支，如果没有master分支的话，github会自动重定向到仓库的默认分支，在我的仓库中，默认分支是main所以实际上访问的是main分支，可以看到这个页面中会列出仓库里有哪些文件、以及一些访问数据等。

这种方式理论上可行，不过由于要替换url（对于文稿中已经大量使用了固定格式的url）实在是有的费时费力，而另一种解决办法就是<等待并心怀希望吧>。

等待，并心怀希望吧！CDN的缓存有一定的时限，在我研究怎么解决的过程中，原本访问不到的资源在慢慢地恢复正常，具体时长不太确定，我折腾了快一个小时，但至少不是毫无收获。

Jsdelivr

Jsdelivr 可以给我们提供对github更快的访问速度，类似一个高速的中转节点，并且我们可以很方便的使用，使用方式是将我们的GitHub仓库访问地址转换为通过jsdelivr访问的链接

在Jsdelivr官网顶部菜单栏里有一个下拉菜单Tools，其中有可以将GitHub仓库转换为jsdelivr链接的选项，将你的仓库地址栏内容复制进去就会自动得到对应的jsdelivr链接

对于 “https://github.com/Avvywenna/Photo"，它会被转换为 “https://cdn.jsdelivr.net/gh/Avvywenna/Photo“, 当然你可以直接复制这里的文本，挑选关键部分改为你自己的对应内容

要留意的点是此处链接结尾没有’/‘符号，这个链接我们会直接应用到PicGo的设置中，而在直接访问jsdelivr上有关这个仓库的数据时，我们需要加上’/‘，就像这样：”https://cdn.jsdelivr.net/gh/Avvywenna/Photo/"，你也可以自己试试，加或者不加会有什么区别。

在接下来的PicGo配置中，我们会需要这个链接（包括更早之前创建的token），所以让我们提前准备好它

题外话

当你尝试在GitHub中打开的一个文件链接转换为jsdelivr时，它会保留分支的信息

例如对于地址https://github.com/Avvywenna/Photo/blob/main/btr1.jpg，经过转换后得到的jsdelivr链接是https://cdn.jsdelivr.net/gh/Avvywenna/Photo@main/btr1.jpg，会发现链接中会带有@main来区分分支，而在不带分支标识时jsdelivr会通过@master来访问默认分支（除非你创建了自己的master分支）

PicGo

  1. 下载并安装。
  2. 打开PicGo，在左侧列表找到图床设置，点击会展开一系列的站点设置，我们将要使用Github作为我们的图床，所以我们选中GitHub，到目前为止我们还没有添加过任何图床，所以在右侧的展示中只有一个空空的”+”，我们点击它，以便我们可以配置我们的第一个图床。
  3. 在仓库名中，我们填Username/Repositryname(替换你自己的)，在分支名中我们填”main”(仓库创建默认的分支)，在Token栏，我们填写我们在稍早就准备好了的Token(别说你找不到了)，最后在自定义域名中，填上我们刚准备好的jsdelivr链接，PicGo会使用这个链接来访问我们的仓库，最后点击确定，完成图床的配置
  4. 可以看到我们的github图床中已经出现了我们的第一个图床，当然我们可以拥有不止一个图床，如果你需要，你可以创建更多
  5. 在上传区我们可以上传我们的图片资源到指定图床，在相册我们可以看到我们所上传的图片（它不会跟图床保持同步，当你在github上手动上传文件时，本地的picGo不会更新到），当我们想在博客中（或者别的什么地方）访问这张图片时，在相册找到目标图片，点击图片底部的复制按钮, 你将会得到一个链接，它大概是长这样的 “https://cdn.jsdelivr.net/gh/Name1/Name2/xxxx.png“, 你可以直接在浏览器地址栏中访问，以确认你得到了你想要的效果。在上传区域，可以选择url的格式，选择其中一个，它会在你复制图片链接时生效。

题外话

我们在PicGo的图床配置设置里面，可以设置自定义域名，在上传和加载图片时，PicGo会走这里配置的自定义域名，在上面我们是使用了jsdelivr来加速我们对github的访问，同时也看到了使用CDN带来的一些影响

如果没有设置自定义域名的话，PicGo会裸连github，经过测试上传的速度确实会不如走CDN转发

之前有段时间我因为连不上github的问题折腾了很多时间，从修改host到科学上网，结果github能正常使用了，正准备上传一些图片的时候，发现picGo又寄了

明明picGo提示上传成功，但是实际上仓库里面并没有上传记录，翻picGo日志查看也没有发生错误的信息，但是在日志里留意到了一条信息，它是在文件上传成功之后，会打印文件的链接，而这条链接是jsdelivr格式的

于是我猜测因为我配置了自定义域名，所以picGo在上传文件的时候并不是直接跟github交互的，而是与jsdelivr的某些接口交互，通过jsdelivr进行上传，当jsdelivr返回成功时，实际上并没有成功上传到github

这一步的问题出现在哪我目前还不得而知，当我在jsdelivr上直接访问仓库内容时，得到的也是没有上传记录的结果

不过我在想会不会是我之前改的host导致的，结果不出所料，在我把host文件还原之后，picGo的上传就恢复正常了
