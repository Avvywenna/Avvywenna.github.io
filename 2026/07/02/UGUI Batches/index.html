Unity UGUI 合批机制深度解析

一、如何观察 UGUI 的渲染数据

在 Unity 编辑器模式下运行场景，可以通过以下方式查看 UI 的渲染性能参数：

1. Game 视窗 Stats 面板

在 Game 视窗右上角点击 Stats 按钮，会弹出性能面板，其中包含：

  • Batches：当前帧的总合批次数（≈ DrawCall 数量）
  • Saved By Batching：通过合批节省的 DrawCall 数量
  • Tris / Verts：当前帧渲染的三角面与顶点数

2. Profiler 窗口 - Rendering

打开 Profiler 窗口（Window → Analysis → Profiler），选中曲线图中的某一帧（Unity 会自动暂停），在左侧 Modules 中找到 Rendering，点击后在下方的 Frame Debugger 中可以看到更详细的渲染数据，包括每个 DrawCall 的详细信息。

3. Profiler 窗口 - UI Details

在 Profiler 左侧 Modules 中找到 UI → UI Details，选中后会展示当前帧所有 UI 元素的合批细节信息，包括：

  • 合批的顺序
  • 每个 Batch 包含哪些 UI 元素
  • 合批被打断的具体原因

💡 重点关注：上述工具中，Batches 是最直观衡量 UI 性能的指标。

二、DrawCall 是什么？

DrawCall 并不是一个具体的函数，而是一系列用于调起 GPU 执行渲染任务的指令。一个 UI 元素要被渲染到屏幕上，需要准备纹理、网格等渲染数据，然后通过 Canvas 发起 DrawCall，将指令和数据发送到 GPU 执行。

DrawCall 的性能开销

一个完整的 DrawCall 过程在 CPU 和 GPU 两侧都会产生开销：

CPU 侧开销

  • 验证渲染状态：检查当前使用的材质、纹理、着色器、混合模式等。如果与上一次 DrawCall 不同，就需要切换状态（如切换纹理）。
  • 准备顶点数据：将需要绘制的物体顶点、UV、颜色等数据从内存整理好，映射到 GPU 可读取的位置。
  • 调用底层图形 API：通过驱动（DirectX、OpenGL、Vulkan、Metal）向 GPU 发送命令，本身就有不小的函数调用开销。
  • 刷新命令缓冲区：CPU 会先积攒一批命令再一起发送给 GPU，但 DrawCall 过多会导致缓冲区频繁刷新，增加额外开销。

GPU 侧开销

  • 重新配置渲染管线：切换不同的着色器程序、纹理单元、混合模式等，累积起来会降低吞吐量。
  • 刷新绘制状态：分批次提交的少量顶点，GPU 可能无法充分发挥并行计算能力。
  • 移动端 Tile-Based 架构的额外代价：主流手机 GPU（如 Mali、Adreno）使用 Tile（区块）渲染架构。一次 DrawCall 可能需要先加载之前渲染好的 Tile 缓存，处理完再写回。频繁切换的小 DrawCall 会大幅增加 Tile 的 Load/Store 次数，导致带宽和功耗激增——这也是移动端 UI 上 DrawCall 超过 50 个就会明显卡顿、发热 的核心原因之一。

合批的作用

通过合批，可以将原本多个独立的 DrawCall 合并，组合为一个更大的网格以及一系列共用数据，只通过一次 DrawCall 完成绘制，从而节省大量冗余开销。

三、Batch 的含义

当两个相邻的 UI 元素使用 同一个图集 以及 相同的材质纹理 时，它们可以被合批。此时这两个 UI 元素的 DrawCall 合并为一个，记作 1 个 Batch。

  • 理想情况：一个 UGUI 界面只消耗 1 个 Batch，即所有 UI 元素的 DrawCall 都被合并。
  • 最坏情况：每一个 UI 元素都各自调用自己的 DrawCall，Batches 随 UI 复杂度线性增长。

在检测窗口中看到的 Batches 数值，反映的就是当前界面一共产生了多少个 DrawCall，间接代表了 UI 的渲染性能。

四、UGUI 合批的核心机制

合批的本质

UGUI 合批的本质是：在同一个 Canvas 下，通过深度计算和排序，将材质 ID 和纹理 ID 相同的相邻 UI 元素的网格合并为一个大网格，用一次 DrawCall 提交给 GPU。

合批的前置条件

两个或多个 UI 元素要参与同一个 Batch，首先需要满足：

  • 使用 同一个图集
  • 使用 相同的材质纹理

但仅仅满足这两个条件并不一定能成功合批。 UGUI 在合批之前，还会执行一套 深度计算 和 排序 流程。

深度计算规则

UGUI 会为每个 UI 元素计算一个 深度值（Depth），规则如下：

场景 Depth 计算方式
元素没有被任何其他元素遮挡 Depth = 0
被一个可合批的元素遮挡 Depth = 被遮挡元素的 Depth
被一个不可合批的元素遮挡 Depth = 底层元素.Depth + 1
被多个元素遮挡 取其中最大的 Depth 值

合批的完整流程

整个合批过程按以下顺序执行：

  1. 深度计算 —— 为每个 UI 元素计算 Depth 值
  2. 排序 —— 按 Depth → MaterialID → TextureID → Hierarchy顺序 依次排序
  3. 合批 —— 遍历排序后的列表，只有相邻且 MaterialID + TextureID 都相同的元素才会被合并为一个 Batch

关键结论：材质纹理相同 ≠ 一定能合批。如果两个相同图集的 Image 中间夹了一个不同材质的元素，且深度计算导致它们在排序后不相邻，合批依然会失败。

深度计算与排序的动机

合批的收益来源于“将相同材质/纹理的 DrawCall 连续提交”。但 UI 属于透明物体，GPU 要求必须按照 “底层 → 顶层” 的遮挡顺序进行渲染，否则半透明混合（如阴影、柔光）效果会错乱。

UGUI 的深度计算机制，正是为了在满足 “遮挡顺序正确”（硬性约束）的前提下，通过重新排列渲染队列，让原本分散在不同 Hierarchy 分支、但深度层级相同的 UI 元素 “物理上相邻”，从而为后续的“材质/纹理合批”创造前提条件。

简单来说：Depth 决定“能不能排在一起”，Texture/Material 决定“排在一起后能不能合并”。先按 Depth 排序，是为了在保证画面正确性的同时，最大化合批收益——牺牲极小的排序 CPU 开销，换取巨大的 GPU 状态切换节省。

五、合批中断的常见原因

1. 渲染顺序被打断

在 Hierarchy 的渲染顺序中，如果两个使用同样图集的 Image 之间，插入了使用另外图集的 Image 或 Text 组件，那么：

  • 这两个同图集 Image 会被分别渲染
  • 中间插入的 UI 元素也会独立渲染
  • 合批被中断

2. Text 组件使用了不同字体或字号

不同的字体、字号会生成不同的字体纹理，因此它们各自独立渲染，无法合批。

📌 动态字体（Dynamic Font）的特殊性：动态字体的纹理是运行时动态生成的。当文本出现新字符时，Unity 会实时将该字符栅格化到字体纹理中，可能触发纹理重建。这意味着同一个 Text 组件在不同帧可能使用不同的字体纹理，导致合批状态不稳定，在 Profiler 中表现为偶发的 Batch 突增。

3. Mask、Outline、Shadow 等组件

  • Mask：基于模板缓冲（Stencil Buffer）实现，会额外增加至少 2 个 DrawCall（一个进入遮罩，一个离开遮罩），且遮罩内外的相同图集元素无法合批。
  • Outline / Shadow：这些效果会生成额外的几何体或改变渲染顺序，从而打断合批。

4. RectTransform 的 Z 值不为 0

如果 UI 元素的 RectTransform 的 localPosition.z ≠ 0，某种程度上会影响UI合批的结果，可能是好的也可能是坏的，从结果上会导致Unity的行为不可预测。Z 值不同不一定会打断合批，但它增加了排序的复杂性，在特定组合下会导致合批失败

5. 空的 Image 组件

即使 Alpha = 0 或没有设置图片，只要组件未被禁用，它依然会产生一个 DrawCall，并可能打断合批。

6. 跨 Canvas 无法合批

不同的 Canvas 属于不同的渲染队列，同一个 Canvas 内的 UI 元素合批时不会跨 Canvas。这也是拆分 Canvas 优化时需要付出的代价之一。

六、UGUI 合批优化策略

根据上述合批中断的原因，可以总结出以下实用的优化规则：

1. 使用 Sprite Atlas

将同一个界面上用到的 Sprite 资源打包到同一个图集。通常做法是按功能模块分文件夹，将同一文件夹的资源打包到一个图集。一个界面应尽量使用最少数量的不同图集。

⚠️ 注意：Unity 2022+ 使用全新的 Sprite Atlas 系统（替代了旧版 Sprite Packer）。对于 UGUI 用的图集，建议保持默认的矩形打包方式，避免开启“Tight Packing”（紧凑打包），因为紧凑打包可能导致 UV 坐标变化，影响合批。

2. 拆分 Canvas（动静分离）

如果界面上有完全静止的背景和频繁更新的数字/图标，可以将它们放在不同的子 Canvas 中。

  • 优点：静态子 Canvas 会被缓存，不会因为动态部分的刷新而重新合批。
  • 代价：每个独立的 Canvas 都会产生 至少 1 个 Batch，且不同 Canvas 之间的 UI 元素无法合批。

💡 适用场景判断：“用少量固定 Batch 换取避免大量动态重建”在车载 HMI 这类界面固定、但部分数据高频刷新的场景下非常有效。但如果界面本身非常简单（少于 15 个元素），拆分反而得不偿失。

3. 使用 RectMask2D 替代 Mask

  • Mask：打断合批，且额外增加至少 2 个 DrawCall。
  • RectMask2D：基于 Shader 裁剪实现，不打断合批，性能远优于 Mask。

⚠️ 注意：多个 RectMask2D 之间的子元素也无法互相合批，使用时仍需适度。

4. 减少使用 Outline / Shadow 等效果

  • 这些效果会额外生成多个顶点，不仅增加 Batches，还会显著增加顶点数量。
  • 如果必须使用，考虑用 Shader 实现 替代组件方式，或者限制使用范围。

5. 谨慎使用 RectTransform 的 Z 值

localPosition.z = 0会将 UI 元素从 2D 平面深度计算中剥离，这一机制的影响取决于具体场景——可能打断合批，也可能促成合批。因此不应无条件“一律归零”，而应在实际场景中通过 Frame Debugger 验证其效果后，再决定是否保留非零 Z 值。

6. 使用自定义 EmptyRaycast 替代空 Image

如果需要一个纯逻辑的点击区域而不产生渲染开销，应创建一个继承自 Graphic 的自定义组件，重写 OnPopulateMesh 并清空网格（vh.Clear()），同时将 raycastTarget 保持为 true。这种方式不产生任何 DrawCall，而使用空 Image 会额外产生一个 DrawCall。

七、UGUI 渲染顺序补充说明

Unity 按照 Hierarchy 从上到下 的顺序遍历 UI 节点：

  • 如果一个节点有子节点，则优先遍历子节点
  • 然后才遍历下一个相邻节点
  • 按照 深度优先 的方式得到一个全局的渲染队列

关键结论：

  • 只要确保能够被合批的对象在渲染队列中连续排列即可。
  • 不同的 Canvas 属于不同的队列，只有同一个 Canvas 内的 UI 才会被合批。
  • 修改节点在 Hierarchy 中的顺序会改变渲染队列，可能导致 Batch 增加，需谨慎操作。

八、常见问题速查表

界面 Batches 突增 Text 动态生成新字符 预加载常用字符，或使用静态字体

九、总结

核心概念 关键点
DrawCall CPU/GPU 发起渲染指令的开销，移动端尤其敏感
Batch 合批后的 DrawCall 数量，是 UI 性能的核心指标
合批条件 同 Canvas + 同材质 + 同纹理 + 深度连续
深度计算 UGUI 合批前的关键步骤，决定元素是否相邻
合批中断原因 不同图集 / 不同字体 / Mask / Z值 / 空Image / 跨Canvas
优化方向 Sprite Atlas / 调整Hierarchy / 动静分离 / RectMask2D
拆分Canvas 牺牲少量固定 Batch，避免大量动态重建

📝 写在最后
UGUI 合批优化是 Unity UI 性能调优中最常被考察、也最容易出效果的环节。
理解其背后的深度计算和排序机制，比死记硬背“用图集、调顺序”更能应对复杂的实际场景。
