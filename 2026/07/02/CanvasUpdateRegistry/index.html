UGUI 源码剖析 —— CanvasUpdateRegistry 调度中心

Created2026-07-02|Updated2026-07-02|UnityUGUI
|Post Views:

一、CanvasUpdateRegistry 是什么？

CanvasUpdateRegistry 是 UGUI 内部的“中央调度室”。它的核心职责是：

  1. 收集：每帧接收来自 Graphic 和 Layout 组件的“脏标记”注册请求。
  2. 调度：在接收到 Canvas.willRenderCanvases 事件后，统一执行 PerformUpdate，按固定顺序调用所有待更新元素的 Rebuild 方法。

它本身是一个单例（通过静态实例 s_Instance 访问），但并非 MonoBehaviour，不挂载在任何 GameObject 上，纯粹是一个逻辑管理类。

二、核心数据结构 —— IndexedSet

CanvasUpdateRegistry 内部维护了两个集合，分别存储待布局重建和待图形重建的元素：

  • m_LayoutRebuildQueue：存储需要布局重建的 ICanvasElement
  • m_GraphicRebuildQueue：存储需要图形重建的 ICanvasElement

这两个集合的类型都是 IndexedSet<T>，这是 UGUI 自定义的一个集合类，它的特点是：

  • 内部同时维护一个 List<T> 和一个 Dictionary<T, int>
  • 保证了元素的唯一性（同一个元素不会被重复加入）
  • 通过 Dictionary 记录每个元素在 List 中的索引，实现了 O(1) 的随机访问和移除
  • 缺点：相比单纯的 List 或 HashSet，会消耗额外的内存来维护字典

为什么不用 List 或 HashSet？

集合类型 唯一性保证 随机移除效率 遍历顺序确定性
List<T> ❌ 需外部保证 O(n) ✅ 有顺序
HashSet<T> ✅ O(1) ❌ 无顺序
IndexedSet<T> ✅ O(1) ✅ 有顺序（按添加顺序）

CanvasUpdateRegistry 需要同时满足：元素唯一、移除高效、遍历顺序稳定 —— 因此选择了 IndexedSet。

三、生命周期与触发时机

CanvasUpdateRegistry 在 Canvas 组件首次启用时，通过静态构造函数将自己注册到 Canvas.willRenderCanvases 事件上：

Canvas.willRenderCanvases += PerformUpdate;

这意味着：

  • 常规路径：每帧 LateUpdate 之后，Unity 引擎调用 SendWillRenderCanvases → 触发 willRenderCanvases 事件 → PerformUpdate 被执行。
  • 强制刷新路径：用户代码调用 Canvas.ForceUpdateCanvases() → 同步触发 PerformUpdate，不依赖 LateUpdate 的时序。

💡 关键理解：PerformUpdate 是同步执行的 —— 它会在当前帧的 willRenderCanvases 事件中被完整执行完毕，不会跨帧。因此，在 PerformUpdate 执行过程中对 UI 的修改，不会立即触发新一轮重建，而是会被标记为“脏”并推迟到下一帧的 willRenderCanvases 事件中处理。

四、PerformUpdate 执行流程

PerformUpdate 是 CanvasUpdateRegistry 最核心的方法，它的执行顺序是固定的，也是理解 UGUI 性能优化的关键。完整流程如下：

第一步：清理无效元素

遍历 m_LayoutRebuildQueue 和 m_GraphicRebuildQueue，检查每个元素是否仍然有效（如 GameObject 是否被销毁）。如果无效，则从队列中移除。

这是 IndexedSet 的优势体现 —— 由于每个元素在集合中都有唯一索引，移除操作只需 O(1) 时间，避免了遍历全集的 O(n²) 开销。

第二步：布局重建（Layout Rebuild）

  1. 标记 m_PerformingLayoutUpdate = true（防止在重建过程中被修改）
  2. 对 m_LayoutRebuildQueue 进行排序：按节点在 Hierarchy 中的深度从深到浅排序。
  3. 遍历排序后的列表，对每个元素按顺序调用 Rebuild(CanvasUpdate.Prelayout)、Rebuild(CanvasUpdate.Layout)、Rebuild(CanvasUpdate.PostLayout)
  4. 标记 m_PerformingLayoutUpdate = false
  5. 调用每个元素的 LayoutComplete 方法
  6. 清空 m_LayoutRebuildQueue

为什么需要排序？

在布局重建时，父节点的尺寸依赖子节点的尺寸（例如 ContentSizeFitter 需要根据子元素内容计算自身大小）。如果先处理父节点再处理子节点，会导致父节点计算时子节点尺寸尚未确定，产生错误的布局结果。因此，必须从最深的子节点开始，自下而上地重建布局。

第三步：裁剪更新（Clipping Update）

调用 ClipperRegistry.Cull()，处理所有 Mask 和 RectMask2D 的裁剪区域计算。这一步在布局确定之后、图形重建之前执行，因为裁剪区域依赖于布局后的最终尺寸。

第四步：图形重建（Graphic Rebuild）

  1. 标记 m_PerformingGraphicUpdate = true
  2. 遍历 m_GraphicRebuildQueue（无需排序，因为图形重建不依赖父子层级关系）
  3. 对每个元素按顺序调用 Rebuild(CanvasUpdate.PreRender) 和 Rebuild(CanvasUpdate.LatePreRender)，生成网格数据
  4. 标记 m_PerformingGraphicUpdate = false
  5. 调用每个元素的 GraphicUpdateComplete 方法
  6. 清空 m_GraphicRebuildQueue

为什么裁剪更新在布局和图形之间？

  • 布局阶段确定了 UI 元素的最终尺寸和位置。
  • 裁剪阶段需要基于这些尺寸计算出裁剪区域。
  • 图形阶段在生成网格时，应用裁剪结果，决定哪些顶点被保留或裁剪掉。

五、关键机制：锁定标志的作用

CanvasUpdateRegistry 使用了两个锁定标志：

  • m_PerformingLayoutUpdate
  • m_PerformingGraphicUpdate

当 Graphic 或 Layout 组件在 Rebuild 过程中被修改（例如触发新的 SetLayoutDirty），注册方法会检查这两个标志：

  • 如果当前正在执行布局重建（m_PerformingLayoutUpdate == true），新的布局脏标记不会立即加入当前队列，而是会被推迟到下一帧。
  • 同理，m_PerformingGraphicUpdate == true 时，新的图形脏标记也会被推迟。

这个机制的意义：防止在 PerformUpdate 执行过程中，队列被不断插入新元素，导致死循环或同一帧内无限膨胀。它保证了每一帧的 UI 重建数量是确定且可控的。

六、优化启示

基于对 CanvasUpdateRegistry 的理解，可以得到以下优化策略：

1. 减少一次性触发大量 Dirty 标记

由于 PerformUpdate 是同步执行的，如果在同一帧内触发了大量 UI 元素的 SetLayoutDirty 或 SetVerticesDirty，它们都会在本帧的 willRenderCanvases 事件中被集中处理，造成明显的 CPU 峰值。因此：

  • 对于包含大量元素的列表更新，避免在同一帧内一次性激活或修改所有子元素。建议采用 分帧更新 策略，每帧只处理 10~20 个元素，将 UI 重建开销分摊到多帧中，避免单帧 CPU 峰值。同时，SetActive(false) 可以在批量修改过程中（如增删子节点时）临时关闭父节点，防止中间状态反复触发脏标记。
  • 避免在 Update 中频繁修改 UI 属性。

2. 理解布局重建的排序代价

布局重建阶段需要对 m_LayoutRebuildQueue 进行排序（按 Hierarchy 深度）。这涉及到比较操作和元素交换，在复杂 UI 中会产生不可忽略的开销。因此：

  • 尽量减少 LayoutGroup 的嵌套层数。
  • 对于静态 UI，考虑禁用 ContentSizeFitter 等自动布局组件，手动设置尺寸。自动布局组件容易导致频繁的LayoutRebuild产生。

3. 图形重建队列无需排序

与布局不同，图形重建阶段不排序，因为 Graphic 的网格生成不依赖父子层级关系。这意味着：

  • 在同一个 Canvas 下，大量 Graphic 的重建开销主要来自网格数据的生成（OnPopulateMesh），而不是排序。
  • 因此，优化图形重建的主要方向是减少网格复杂度（如降低顶点的数量），而非调整 Hierarchy 顺序。

4. 利用锁定机制避免运行时频繁注册

由于 m_PerformingLayoutUpdate 和 m_PerformingGraphicUpdate 的存在，在同一帧内对 UI 的二次修改会被延迟到下一帧处理。这意味着：

  • 如果你的业务逻辑需要在同一个帧内“修改 UI → 获取 UI 尺寸 → 再修改 UI”，应该使用 Canvas.ForceUpdateCanvases() 强制立即刷新，而非依赖自然调度。
  • 但 ForceUpdateCanvases 本身会带来显著的性能开销，应谨慎使用。

七、与 Graphic、Batcher 的关系

组件 职责
Graphic 生成网格数据，标记脏状态
CanvasUpdateRegistry 收集脏元素，调度 Rebuild 顺序
ICanvasElement 统一的 Rebuild 接口，由 Graphic 和 LayoutGroup 实现
Canvas 在每帧末尾触发 willRenderCanvases 事件，最终发起 DrawCall

CanvasUpdateRegistry 是连接 “脏标记产生” 与 “网格数据生成” 的桥梁。没有它，Graphic 的修改不会自动触发重建；没有 Canvas 的 willRenderCanvases 事件，PerformUpdate 也不会被调用。

它们共同构成了 UGUI 渲染管线的调度层。

八、总结

核心概念 关键点
角色 UGUI 的中央调度中心，收集脏元素并统一重建
数据结构 IndexedSet：唯一性 + O(1) 移除 + 稳定遍历顺序
触发时机 LateUpdate 后的 willRenderCanvases 事件，或 ForceUpdateCanvases() 强制触发
执行顺序 清理无效 → 布局重建（排序）→ 裁剪更新 → 图形重建（不排序）
布局排序原因 父节点尺寸依赖子节点，必须自下而上重建
锁定标志 防止在重建过程中队列被修改，确保一帧内处理次数可控
优化方向 减少单帧脏标记数量 / 减少布局嵌套层级 / 谨慎使用 ForceUpdateCanvases
