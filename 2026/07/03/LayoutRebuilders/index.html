UGUI 源码剖析 —— LayoutRebuilder

Created2026-07-03|Updated2026-07-03|UnityUGUI
|Post Views:

一、LayoutRebuilder 是什么？

LayoutRebuilder 是 UGUI 布局系统的 “执行器”。它的核心职责是：

  1. 触发布局重建：提供 MarkLayoutForRebuild 和 ForceRebuildLayoutImmediate 两个入口，启动布局计算流程。
  2. 执行布局计算：在 Rebuild 方法中，按“水平 → 垂直”、“子节点 → 父节点 → 子节点”的顺序，完成所有 ILayoutElement 的尺寸计算和位置控制。
  3. 对接调度中心：自身实现 ICanvasElement 接口，可以注册到 CanvasUpdateRegistry 的 m_LayoutRebuildQueue 中，参与统一的 UI 重建管线。

二、为什么需要 LayoutRebuilder？

Graphic 可以直接将自己注册到 CanvasUpdateRegistry，但 Layout 组件不行。原因在于：

  • 一个 LayoutGroup 的布局重建，不仅仅影响自身，还会递归影响其父节点和子节点。
  • 同一帧内可能有多个布局组件同时被标记为“脏”，需要统一排序（按层级深度自下而上）后再执行。

LayoutRebuilder 的作用就是作为 “中间代理层”：

  • 收集所有需要布局重建的元素
  • 在 PerformUpdate 的布局阶段，统一按正确的顺序执行计算
  • 避免每个 Layout 组件各自独立触发重建，造成重复计算和性能浪费

三、对象池机制

LayoutRebuilder 没有像 Graphic 那样直接依附在 GameObject 上。它本身只是一个逻辑对象，通过 对象池 复用，以避免频繁创建和销毁造成的 GC 压力。

具体实现如下：

  • LayoutRebuilder 维护了一个静态的 ObjectPool<LayoutRebuilder> 对象池。
  • 当需要触发布局重建时，通过 Get() 从池中获取一个实例，并用目标 RectTransform 初始化。
  • 在完成重建后，通过 Release() 将实例释放回池中。

与 Graphic 的区别：

类型 实例管理方式
Graphic 直接挂载在 GameObject 上，随对象生命周期存在
LayoutRebuilder 从对象池获取，使用完释放回池，不长期持有

四、两种触发方式

1. MarkLayoutForRebuild（异步，推荐）

这是常规的触发方式。当布局组件检测到自身或其子元素发生变化时，调用此方法，将自身注册到 CanvasUpdateRegistry 的待布局重建队列中，由引擎在每帧末尾的 PerformUpdate 中统一处理。

调用链为：

  • 布局组件调用 LayoutRebuilder.MarkLayoutForRebuild(rectTransform)
  • MarkLayoutForRebuild 内部获取一个 LayoutRebuilder 实例，并以 rectTransform 为目标进行初始化
  • 调用 CanvasUpdateRegistry.TryRegisterCanvasElementForLayoutRebuild(builder)，将实例添加到 m_LayoutRebuildQueue 中
  • PerformUpdate 的布局阶段，遍历队列，调用每个 LayoutRebuilder 的 Rebuild 方法
  • LayoutRebuilder 实例最终在 LayoutComplete 中回收

2. ForceRebuildLayoutImmediate（同步，谨慎使用）

此方法会 立即同步执行 布局重建，不依赖 willRenderCanvases 事件。

调用链为：

  • 调用 LayoutRebuilder.ForceRebuildLayoutImmediate(rectTransform)
  • 从对象池获取 LayoutRebuilder 实例，调用其 Rebuild 方法
  • 重建完成后立即释放

适用场景：需要在同一帧内立即获取布局后的尺寸（如在 Start 中计算子元素的最终位置）。

注意事项：这是一个 重量级操作，会递归计算所有子元素的尺寸，频繁调用会导致明显的性能下降。

五、Rebuild 方法的执行流程

Rebuild 是 LayoutRebuilder 最核心的方法，它在 PerformUpdate 的布局阶段被调用，并按 CanvasUpdate 枚举的阶段顺序执行：

阶段一：水平方向计算（自下而上）

  • 调用 ILayoutElement.CalculateLayoutInputHorizontal()
  • 从 最深的子节点 开始，逐级向上计算每个元素的 minWidth、preferredWidth、flexibleWidth 等水平尺寸数据
  • 父节点依赖子节点提供的尺寸数据来计算自身尺寸

为什么水平先于垂直？

这是一个代码设计层面的约定：

  • 水平计算过程中，不允许依赖 RectTransform 的尺寸属性（如宽度、位置），只计算并缓存数值结果。
  • 垂直计算过程中，可以依赖水平计算的结果。例如，一个 Text 组件可以在水平宽度确定后，再根据该宽度计算垂直方向上的高度。

这种设计确保了计算过程是 确定且无环的。

阶段二：水平方向控制（自上而下）

  • 调用 ILayoutController.SetLayoutHorizontal()
  • 从 父节点 开始，逐级向下，根据之前计算得到的尺寸数据，修改每个元素的 RectTransform 的宽度和位置

阶段三：垂直方向计算（自下而上）

  • 调用 ILayoutElement.CalculateLayoutInputVertical()
  • 从最深的子节点开始，逐级向上计算每个元素的 minHeight、preferredHeight、flexibleHeight 等垂直尺寸数据
  • 此时可以依赖水平计算阶段缓存的宽度数据

阶段四：垂直方向控制（自上而下）

  • 调用 ILayoutController.SetLayoutVertical()
  • 从父节点开始，逐级向下，根据之前计算得到的尺寸数据，修改每个元素的 RectTransform 的高度和位置

关键点：

  • 计算阶段只读取数据、只缓存结果，不修改 RectTransform
  • 控制阶段才真正应用尺寸和位置修改

六、布局计算的“自下而上”和“自上而下”

之前在学习 CanvasUpdateRegistry 时已经了解：布局重建必须按层级深度从深到浅排序。这正是因为布局计算遵循以下依赖链：

  1. 子节点 → 父节点（计算阶段）：父节点的 preferredWidth 取决于所有子节点的总宽度，因此必须先计算子节点，再计算父节点。
  2. 父节点 → 子节点（控制阶段）：子节点的最终位置取决于父节点的尺寸和布局排列规则，因此必须先设置父节点，再设置子节点。

LayoutRebuilder 的 Rebuild 流程完美地遵循了这两条依赖链。

七、与 CanvasUpdateRegistry 的协作细节

在 CanvasUpdateRegistry 中，有一类方法叫 TryRegisterCanvasElementForLayoutRebuild，其返回值是一个 bool。在 LayoutRebuilder 中的使用逻辑如下：

  • 当 LayoutRebuilder 实例调用 TryRegisterCanvasElementForLayoutRebuild 时，如果该实例尚未在队列中，则返回 true，表示注册成功。
  • 如果该实例 已经存在于队列中（即同一元素在同一帧内被多次标记为脏），则返回 false。
  • 当返回 false 时，说明本次注册是“重复的”，LayoutRebuilder 会将刚新建的实例 释放回对象池。

这个细节说明了之前看到的 IndexedSet 去重机制在这里是有效的。

八、与 Graphic、CanvasUpdateRegistry 的关系

组件 职责 是否参与深度排序
Graphic 生成网格数据，标记脏状态 否（图形重建不排序）
LayoutRebuilder 执行布局计算，控制尺寸和位置 是（布局必须自下而上）
CanvasUpdateRegistry 收集脏元素，调度重建顺序 ——

LayoutRebuilder 的布局计算为 Graphic 的网格生成提供了 正确的尺寸和位置数据，而 CanvasUpdateRegistry 则确保了两者在正确的顺序下执行。

九、优化启示

基于对 LayoutRebuilder 的理解，可以进一步明确以下优化策略：

1. 减少不必要的布局重建

  • 避免在 Update 中频繁修改会触发 SetLayoutDirty 的属性（如 RectTransform.sizeDelta、Text.text 等）
  • 批量修改时，先将父节点 SetActive(false)，完成修改后再激活，将多次脏标记合并为一次重建

2. 理解 ForceRebuildLayoutImmediate 的代价

  • ForceRebuildLayoutImmediate 会同步执行完整的布局计算（水平计算 + 水平控制 + 垂直计算 + 垂直控制），递归遍历所有子节点
  • 在 Update 或循环中频繁调用会导致明显的性能下降
  • 仅当需要在同帧内立即获取布局后的尺寸时才使用

3. 布局嵌套层数的影响

  • 布局重建时需要对 m_LayoutRebuildQueue 进行排序（按层级深度），嵌套越深，排序开销越大
  • 应尽量减少 LayoutGroup 的嵌套层数，或将嵌套布局拆分为多个独立的 Canvas

4. 对象池规避 GC

  • LayoutRebuilder 使用对象池复用实例，避免了频繁创建对象产生的 GC Alloc
  • 在日常开发中，可参考这种设计模式，在需要频繁创建临时对象的场景下使用对象池

十、总结

核心概念 关键点
角色 UGUI 布局系统的执行器，负责计算和控制布局
触发方式 MarkLayoutForRebuild（异步） / ForceRebuildLayoutImmediate（同步）
对象池 复用 LayoutRebuilder 实例，避免 GC 压力
执行顺序 水平计算 → 水平控制 → 垂直计算 → 垂直控制
计算方向 自下而上（子节点 → 父节点）
控制方向 自上而下（父节点 → 子节点）
与 Registry 协作 注册到 m_LayoutRebuildQueue，参与统一调度；重复注册时释放实例回池
优化方向 减少嵌套层级 / 批量修改时使用 SetActive(false) 包裹 / 避免频繁调用 ForceRebuildLayoutImmediate

📝 写在最后
LayoutRebuilder 是 UGUI 布局系统的核心执行器，也是之前学习的 Graphic 和 CanvasUpdateRegistry 之间的关键纽带。
理解它的计算顺序和控制逻辑，才能从根本上理解为什么布局操作会带来性能开销，以及如何在实际项目中写出高效的 UI 代码。
至此，UGUI 的渲染调度链路基本完整：脏标记 → 调度中心 → 布局执行 → 图形重建 → 合批渲染。
